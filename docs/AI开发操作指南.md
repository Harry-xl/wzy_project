## 一、改造概要

### 做了什么？

你的项目文件夹从「传统代码目录」变成了 **AI 原生开发环境**。

**之前**：代码文件 + 一个文档，AI 全靠猜。
**现在**：每个目录、每个文件都在告诉 AI ——「这是什么、怎么改、规矩是什么、怎么检查质量」。

### 核心文件结构

```
项目根目录/
│
├── CLAUDE.md                    ← 🔑 AI 入口：每次对话自动加载
│
├── .claude/                     ← 🧠 AI 大脑
│   ├── rules/      (10个文件)   ← 告诉 AI「规范和规矩」
│   ├── skills/     (10个文件)   ← 告诉 AI「怎么做某件事」
│   ├── agents/     ( 6个文件)   ← AI 的不同角色（架构师/开发/测试…）
│   ├── templates/  ( 6个文件)   ← 文档模板（PRD/技术规格/审查清单…）
│   └── prompts/    ( 3个文件)   ← 对话提示词模板
│
├── docs/                        ← 📚 人类阅读的文档
├── tests/                       ← 🧪 自动化测试
├── scripts/                     ← 🔧 运维脚本
│
├── .gitignore                   ← Git 忽略规则
├── .env.example                 ← 环境变量模板（复制为 .env 使用）
├── .editorconfig                ← 编辑器格式统一
└── requirements-dev.txt         ← 开发工具依赖
```

### 两种记忆的区别

| | CLAUDE.md | Auto Memory |
|---|---|---|
| 谁写？ | 你手动编写 | AI 自动记录 |
| 放什么？ | 规则、约定、架构 | 构建命令、调试经验、代码偏好 |
| 在哪？ | 项目根目录 / `~/.claude/` | `~/.claude/projects/star-pal/memory/` |
| 什么时候更新？ | 你编辑 | AI 自动 |
| 适合什么？ | 团队共享、版本控制 | AI 个性化的跨会话记忆 |

## 二、快速上手

### 场景 1：提一个新功能需求

**❌ 错误方式**：
> "帮我加个排行榜"

AI 不知道：什么排行榜？排什么？给谁看？什么样式？——导致 AI 瞎猜，代码质量差。

**✅ 正确方式**：
> "我想加一个学习排行榜功能，帮我按需求工程流程来做"

AI 会：
1. 加载 `.claude/rules/requirement-engineering.md`
2. 按 4 维度提问澄清（目标/范围/约束/优先级）
3. 生成 PRD → 你审批
4. 生成技术设计 → 你审批
5. 拆解为原子任务 → 你审批
6. 逐任务实现（每步跑测试）
7. 质量门禁验证
8. 交付

### 场景 2：修复一个 Bug

**✅ 正确方式**：
> "Bug：登录后跳转到仪表盘时偶尔白屏，帮我按 Bug 修复流程处理"

AI 会：复现 → 定位根因 → 写复现测试 → 修复 → 回归验证。

### 场景 3：重构代码

**✅ 正确方式**：
> "server/app.py 太长了，帮我按重构流程拆分成蓝图架构"

AI 会：确认测试覆盖 → 提取函数/类 → 验证测试通过 → 完成。

## 三、完整开发流程

这是 AI 在此项目中的标准开发链路（8 个阶段）：

```
用户说「我想加一个 XXX 功能」
    │
    ▼
┌─────────────────────────────────────────────┐
│ 阶段 1: 需求捕获                            │
│ AI 提问：目标？范围？约束？优先级？          │
│ 你回答                                     │
│ → 输出：用户故事草稿                        │
│ → 你确认：理解正确 ✅                       │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ 阶段 2: 需求分析                            │
│ AI 探索代码 → 识别影响模块 → 评估风险       │
│ → 输出：影响分析 + 复杂度预估 (S/M/L/XL)    │
│ → 你确认：分析合理 ✅                       │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ 阶段 3: 需求规格化                          │
│ AI 生成 PRD（产品需求文档）                 │
│ 包含：背景/用户故事/验收标准/非功能需求      │
│ → 输出：完整 PRD                            │
│ → 你批准：「可以，进入设计阶段」            │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ 阶段 4: 技术设计                            │
│ AI 生成技术规格                              │
│ 包含：API 设计/DB 变更/前端方案/测试策略     │
│ → 输出：技术规格文档                        │
│ → 你批准：「开始开发吧」                    │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ 阶段 5: 开发实施                            │
│ AI 逐任务实现：                              │
│ DB 迁移 → DAO → Service → Route → Frontend  │
│ 每步：写测试 → 写代码 → 跑测试 → 自审查    │
│ → 输出：代码 + 测试                         │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ 阶段 6: 质量验证                            │
│ AI 执行代码审查清单（6 维度）                │
│ 安全/正确性/性能/风格/文档/测试              │
│ → 输出：审查报告 + 测试报告                 │
│ → 你批准：「通过，准备发布」                │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ 阶段 7: 交付归档                            │
│ AI 生成 Release Notes，更新文档和 changelog │
│ → 输出：可运行代码 + 完整文档               │
└─────────────────────────────────────────────┘
```

### 你需要做什么？

每个阶段你只需要做一件事：**看 AI 的输出，确认或提出修改意见，然后说「继续」**。

你不是在写代码，你是在 **审核 AI 的工作**。这是 AI 开发的核心心智转变。

## 四、需求创造：让 AI 主动帮你发现需求

### AI 什么时候会主动建议？

AI 被配置为在以下情况主动向你提建议：

| 触发信号 | AI 会建议什么 |
|---------|-------------|
| 数据中用户重复错同一类型题 | 知识点专题训练功能 |
| API 响应慢 | 性能优化方案 |
| 代码过长/重复 | 重构时机 |
| 发现未使用的代码 | 功能完善或清理 |
| 题库数量增长 | 模拟考试模式 |
| 用户学习时间分散 | 每日学习提醒/目标设定 |

### AI 主动建议的格式

```
💡 建议：我注意到 [观察到的现象]

分析：[这意味着什么]

建议方案：[具体建议]

预期收益：[价值]

你觉得值得探讨吗？
```

你可以回复「展开说说」让 AI 进入需求工程流程，或者「以后再说」跳过。

### 你也可以主动触发

> "分析一下最近的答题数据，看看有什么可以优化的"
> "审查一下项目的技术债务，建议优先修复哪些"
> "对标一下同类学习平台，看看我们缺什么功能"

## 五、日常开发操作

### 启动项目
```bash
run_all.bat              # 一键启动（Flask 3001 + 静态 8888）
# 或
scripts\start.bat        # 新脚本位置
```

### 运行测试
```bash
scripts\test.bat         # 运行测试 + 覆盖率
# 或
python -m pytest tests/ -v
python -m pytest tests/ --cov=. --cov-report=html
```

### Git 操作
```bash
git status                          # 查看变更
git add <files>                     # 暂存文件
git commit -m "feat: 描述"          # 提交
git checkout -b feature/xxx         # 开新分支
```

### 查看 AI 理解了什么
```
/context     # 查看当前上下文窗口中加载了什么
/memory      # 查看/编辑 AI 的自动记忆
```

### 遇到问题
```
/doctor      # 诊断 AI 配置问题
/clear       # 清空对话，重新开始
/resume      # 恢复之前的对话
```

## 六、质量保障体系

### 每行代码经过的检查

```
AI 写代码时：
  ├── 自动应用 .claude/rules/ 中的规范（Python/JS/CSS/API/DB/安全）
  ├── 每步写完就跑测试：python -m pytest tests/ -v
  └── 自审查代码

AI 完成后的门禁（开发→验证）：
  ├── ✅ python -m pytest tests/ -v → 全部通过
  ├── ✅ pytest --cov → 覆盖率 ≥ 80%
  ├── ✅ 代码审查清单通过（安全/正确性/性能/风格/文档/测试）
  ├── ✅ 无硬编码密钥
  ├── ✅ 文档已更新
  └── ✅ Windows 冒烟测试通过
```

### 代码审查 6 维度

| 维度 | 示例检查项 |
|------|-----------|
| 🔴 安全 | 无硬编码密钥、SQL 参数化、输入验证 |
| 🟡 正确性 | 边界条件处理、事务正确、资源释放 |
| 🟠 性能 | 查询使用索引、无 N+1 查询、分页 |
| 🔵 风格 | PEP 8/ES6+ 合规、类型提示、命名一致 |
| 🟢 文档 | API 有文档、复杂逻辑有注释 |
| 🟣 测试 | 新功能有测试、Bug 有回归测试、Mock 外部 API |

## 八、最佳实践

### 1. 提需求时给上下文，不要给方案

| ❌ 不推荐 | ✅ 推荐 |
|----------|--------|
| "加一个 Redis 缓存" | "用户画像数据加载有点慢，帮我分析一下原因并给出优化方案" |

原因：你可能不需要 Redis，AI 可能找到更简单的方案。

### 2. 每个阶段审批，不要一路绿灯

AI 8 个阶段的流程设计是为了 **让你在错误发生前纠正它**。
- PRD 阶段改需求 = 5 分钟对话
- 开发完再改需求 = 半天返工

### 3. 善用需求创造

每隔 1-2 周，让 AI 分析项目状态：
> "分析一下项目当前的状况，有什么值得优化的？"

### 4. 保持 CLAUDE.md 更新

当你发现 AI 反复犯同样的错误时，不要每次纠正，而是：
> "把这个规则记住，加入 CLAUDE.md"
> 或手动编辑 `CLAUDE.md` 添加规则

### 5. 信任但验证

AI 会遵循规则，但仍可能出错。关键决策点你审批，代码质量靠质量门禁和测试保证。

### 6. 利用模板

当需要正式文档时：
> "用 PRD 模板帮我写 XXX 功能的需求文档"
> "用技术规格模板设计 XXX 的方案"

## 进阶：理解这套体系的运作原理

### AI 打开你的项目时发生了什么？

```
1. 加载系统提示
2. 加载自动记忆 (~/.claude/projects/star-pal/memory/MEMORY.md)
3. 加载环境信息
4. 加载 ~/.claude/CLAUDE.md（你的跨项目偏好）
5. 加载 ./CLAUDE.md（本项目 AI 指南）
6. 需要时加载 .claude/rules/ 下的规则
7. 需要时加载 .claude/skills/ 下的技能

→ 所有这些让 AI 在动手前就「懂」了你的项目
```

### 这套体系的 3 层设计

```
第 3 层: Skills (技能)     ← 「怎么做一个具体任务」（添加功能、修复Bug…）
第 2 层: Agents (角色)     ← 「以什么身份工作」（架构师、后端、测试…）
第 1 层: Rules (规则)       ← 「必须遵守的规矩」（编码、安全、测试…）

基础层: CLAUDE.md           ← 「这个项目是什么」
```

### 需求创造的设计哲学

传统 AI 开发：用户说 → AI 做（**被动**）
本体系：用户说 → AI 澄清 → 确认 → 设计 → 实现 → 验证 → 交付（**规范化主动**）
进阶：AI 观察 → 发现机会 → 主动建议 → 用户确认 → 进入开发流程（**需求创造**）

需求创造不是 AI 凭空发明，而是 AI 基于数据、代码分析、用户行为模式，**帮助用户看见自己没看见的需求**。

## 2. 背景与问题

### 2.1 当前状态

StarPal 已完成 Phase 1 知识库+RAG 系统搭建：
- **ChromaDB** 向量数据库已就绪（32 个知识块已索引）
- **5 个知识库 API** 端点可正常调用
- **AI 对话** 已集成 RAG，可返回带来源引用的回答
- **知识点体系**：`knowledge_sub_topics` 表已有 71 个子知识点 + `knowledge_relations` 表已有 47 个关系
- **工具链**：`tools/pdf_ocr/` 已开发完成，支持命令行 OCR + RAG 入库

**⚠️ 当前知识库内容是 LLM 生成的占位数据**，非真实教材内容。系统虽然有知识点框架，但缺乏真实学习资料来填充。

**🎯 本次升级确立双轨知识架构：**

**首期目标**：管理员先通过上传通道导入《计算机网络》(谢希仁 第8版) 扫描 PDF，作为系统知识库的权威内容，替换当前占位数据。

### 2.2 用户痛点

1. **知识库空转**：知识点框架搭好了，但里面没有真实教材内容——AI 回答只能靠模型记忆
2. **无法个性化**：每个学生的资料不同（不同教材版本、笔记、论文），当前是"一刀切"的知识库
3. **资料混乱**：学生手头有 PDF 教材、Word 笔记、扫描试卷，但没有工具把它们整合成一个"个人知识体系"
4. **缺乏全局视野**：学生不知道自己的资料覆盖了哪些知识点、哪些还没覆盖
5. **门槛高**：命令行 OCR 工具普通学生无法使用——需要图形化操作

### 2.3 预期价值

**双轨知识架构 = 系统知识库 + 个人资料库**，每轨均具备「知识整理可视化 + RAG 检索增强」两大能力。

```
                        ┌──────────────────────────────────────┐
                        │         StarPal 知识体系              │
                        │                                      │
  管理员上传 ──────────► │  ┌────────────────────────────────┐ │
  (教材扫描PDF)          │  │  系统知识库 (user_id=NULL)       │ │
                        │  │  • 知识整理: 统一知识图谱(全局)   │ │──► 所有用户共享
                        │  │  • RAG: AI基于权威教材回答       │ │    权威知识来源
                        │  └────────────────────────────────┘ │
                        │                                      │
                        │  ┌────────────────────────────────┐ │
  用户上传 ────────────► │  │  个人资料库 (user_id=用户ID)    │ │
  (笔记/论文/试卷)       │  │  • 知识整理: 统一知识图谱(个人) │ │──► 个性化学习资料
                        │  │    所有个人资料合并为一张图谱     │ │    AI引用我的资料
                        │  │    支持按知识点/按资料双维度下钻  │ │
                        │  │  • RAG: AI基于个人资料回答       │ │
                        │  └────────────────────────────────┘ │
                        │                                      │
                        │  AI 对话检索范围切换:                  │
                        │  🌐 系统知识库 ←→ 📚 我的资料         │
                        └──────────────────────────────────────┘
```

**关键设计决策：统一知识图谱 + 维度下钻 (方案 C)**

> 用户上传多份资料后，所有个人资料**合并为一张统一的知识图谱**（全局视角，一眼看清覆盖度）。同时支持：
> - **知识点维度下钻**：点击图谱节点 → 查看该知识点来自哪些资料、各贡献了多少内容
> - **资料维度视图**：知识清单页 Tab 切换「按知识点」↔「按资料」，反向查看每份资料覆盖了什么

## 3. 目标与成功标准

### 3.1 业务目标

- 目标 1：用户可在 3 分钟内完成「上传资料 → 等待处理 → AI 问答验证」的闭环
- 目标 2：用户上传的资料在 AI 对话中可检索、可引用，回答带来源标注
- 目标 3：用户能直观看到资料库状态（文档数、块数、处理进度）

### 3.2 可量化成功指标 (KPI)

- 指标 1：80% 的用户能在首次使用后成功完成一次资料上传+入库
- 指标 2：个人资料检索命中率 > 60%（切换「我的资料」后提问，回答引用个人资料的比例）
- 指标 3：知识清单中知识点自动映射准确率 > 70%（人工抽检 20 个知识块）
- 指标 4：400 页扫描 PDF 全流程 < 30 分钟；文字 PDF/Word < 2 分钟
- 指标 5：用户上传资料后，知识图谱覆盖度从 0% → 可见提升（如覆盖 15+ 知识点）

### 4.1 主要用户故事

- **US-A02**: 作为**学生用户**，我希望**查看统一的「知识图谱」**（所有个人资料合并为一张知识点关联关系图，节点颜色反映覆盖度），以便**从全局视角理解各知识点之间的联系，找到学习薄弱环节**

- **US-B01**: 作为**学生用户**，我希望**上传自己的教材/笔记 PDF/Word**，以便**AI 对话能引用我的资料内容回答问题，与系统知识库形成互补**

**通用能力**

- **US-C01**: 作为**学生用户**，我希望**在仪表盘看到资料库状态**（处理进度、覆盖率变化），以便**确认资料已成功入库可用**

- **US-C02**: 作为**学生用户**，我希望**管理已上传的资料**（查看/删除），以便**保持资料库整洁**

### 4.2 次要场景 / 边缘用例

- **场景 A（空状态）**：新用户首次打开「我的资料库」→ 显示引导页「还没有上传资料，点击上传你的第一份学习资料」
- **场景 B（处理失败）**：上传的 PDF 损坏/无法识别 → 显示失败状态 + 错误原因 + 重新上传按钮
- **场景 C（重复上传）**：用户上传了相同文件 → 提示「此文件已存在」并提供「覆盖」或「跳过」选项
- **场景 D（超大文件）**：用户上传了 > 500MB 的 PDF → 提示文件过大，建议压缩后上传
- **场景 E（不支持格式）**：用户上传了 .ppt / .epub 等格式 → 提示格式不支持，列出支持的格式

#### 通用底层：资料上传与处理

**双轨上传通道：**

| 通道 | 入口 | 访问者 | `knowledge_documents.user_id` | 检索归属 |
|------|------|--------|:---:|------|
| 系统上传 | 管理后台 (admin.html) | 管理员 | `NULL` | 「系统知识库」 |
| 个人上传 | 仪表盘「我的资料库」 | 登录用户 | 用户 ID | 「我的资料」 |

**共用处理管线**（系统上传和个人上传走同一套管线，仅入库时的 `user_id` 不同）：

**前端 — 上传与管理（个人端）：**

- [ ] **上传入口**：仪表盘侧边栏新增「📚 我的资料库」入口，页面内拖拽上传区域 + 点击选择文件
- [ ] **文件支持**：扫描 PDF（OCR）、文字 PDF（提取）、Word .docx（提取），自动检测类型
- [ ] **上传配置**（可折叠）：文档标题、文档类型（教材/RFC/论文/笔记/其他）
- [ ] **处理进度**：上传后实时进度条（已处理页数/总页数 + 预计剩余时间），SSE 推送
- [ ] **文档列表**：每项显示文件名、类型图标、大小、上传时间、状态（处理中⏳/已就绪✅/失败❌+原因）
- [ ] **删除文档**：确认对话框 → 级联删除（文件 + MySQL 知识块 + ChromaDB 向量）
- [ ] **空状态引导**：首次使用显示「还没有资料，上传你的第一份学习资料吧」

**前端 — 上传与管理（管理端）：**

- [ ] **管理后台新增「系统知识库」板块**：上传区域 + 文档列表，与个人端 UI 一致但面向系统资料
- [ ] **系统文档管理**：查看处理进度、删除/重传系统资料
- [ ] **上传类型提示**：引导上传权威教材（如《计算机网络》第8版扫描 PDF）

**后端 — 处理管线：**

- [ ] `POST /api/library/upload` — 文件上传（multipart/form-data），`user_id` 参数区分系统/个人：
  - `user_id = 0` 或 `null` → 系统知识库（管理员）
  - `user_id = 具体值` → 个人资料库（普通用户）
- [ ] **统一处理调度器**：自动检测文件类型 → 路由到对应处理器
  - 扫描 PDF → PaddleOCR 管线
  - 文字 PDF → PyMuPDF 直接提取文本
  - Word → python-docx 提取文本
- [ ] **后台异步**：上传后立即返回 task_id，后台线程处理
- [ ] `GET /api/library/progress/<task_id>` — SSE 实时进度
- [ ] `GET /api/library/documents` — 文档列表（`user_id` 参数过滤：0=系统资料，其他=个人资料）
- [ ] `DELETE /api/library/documents/<doc_id>` — 级联删除

#### 能力 A：知识整理与可视化

> **核心设计 (方案 C)**：用户上传多份资料后，**所有个人资料合并为一张统一的知识图谱**。系统知识库同理——所有系统资料合并为一张全局图谱。支持知识点维度下钻和资料维度切换。

**A1. 知识清单 (Knowledge List)**

> 资料处理后，系统自动分析内容 → 映射到知识点体系 → 生成覆盖清单。**所有资料合并展示，支持双维度切换。**

- [ ] **知识点维度视图（默认 Tab「🏷️ 按知识点」）**：表格展示 71 个子知识点体系，每行标注：
  - 知识点名称
  - 覆盖状态：「✅ 已覆盖（3 份资料, 15 个知识块）」/ 「⚠️ 部分覆盖」/ 「— 未覆盖」
  - 展开行 → 列出贡献该知识点的所有资料及块数（**下钻**）
- [ ] **资料维度视图（Tab「📄 按资料」）**：反过来看——每份资料覆盖了哪些知识点，每个知识点有多少块
- [ ] **清单筛选**：按知识点大类筛选（计算机网络概述/网络体系结构/传输层...）
- [ ] **自动映射机制**：文件处理完成后 → 每个 chunk 向量与 71 个子知识点描述向量计算余弦相似度 → 超过阈值则关联 → 写入 `knowledge_chunks.sub_topic_id`

**A2. 知识图谱 (Knowledge Graph)**

> 统一力导向图，所有资料的知识点映射合并渲染。节点=知识点，连线=关联关系，颜色/大小反映用户覆盖度。

- [ ] **统一知识图谱可视化**：使用 ECharts 力导向图 (`type: 'graph'`)
  - **所有个人/系统资料合并为一张图**（不是每篇资料独立一张图）
  - 节点颜色表示覆盖度：绿色=已覆盖，黄色=部分覆盖，灰色=未覆盖
  - 节点大小表示关联资料量（覆盖越多，节点越大）
  - 连线表示知识点关系（前置依赖/关联/扩展/组成部分）
- [ ] **节点点击下钻**（关键交互）：
  - 点击节点 → 弹出详情面板，展示：
    - 关联文档列表（哪些资料覆盖了此知识点）
    - 各文档贡献的知识块数量
    - 知识块内容摘要（前 3 块）
    - 「查看完整内容」链接 → 跳转到对应文档
- [ ] **图谱交互**：缩放、拖拽、节点悬停高亮关联节点
- [ ] **覆盖度总览**：环形图显示「已覆盖 45/71 知识点 (63%)」
- [ ] **推荐补充**：高亮闪烁「核心但未覆盖」的知识点节点（重要性高但覆盖度为 0 → 建议上传相关教材章节）

**后端 — 知识分析 API：**

- [ ] `GET /api/library/knowledge-coverage` — 用户知识点覆盖数据（含 `user_id` 过滤；系统级 `user_id=0` 查全局）
- [ ] `GET /api/library/knowledge-graph` — 知识图谱数据（节点+关系+覆盖度，含 `user_id` 过滤）
- [ ] `GET /api/library/knowledge-node-detail?sub_topic_id=X&user_id=Y` — 节点下钻详情（关联文档+chunks）
- [ ] `POST /api/library/analyze/<doc_id>` — 触发单个文档的知识点映射（处理管线自动调用）
- [ ] **知识点自动映射算法**：每块文本 → EmbeddingService 向量 → 与 71 个子知识点的描述向量做余弦相似度 → 超过阈值则关联

### 5.3 不包含 (Out of Scope)

- [ ] **题目自动生成**：从资料内容生成练习题（延后到 Phase 3）
- [ ] **资料共享**：用户间共享/公开资料（延后，需权限系统）
- [ ] **手动编辑知识点映射**：自动映射结果不可手动修改（先做好自动，延后加人工校正）
- [ ] **资料全文搜索**：在资料库页面搜索已上传文档的全文（延后）
- [ ] **批量上传**：一次上传多个文件（延后）
- [ ] **移动端适配**：桌面端优先
- [ ] **系统知识库图谱与个人知识图谱合并**：系统和个人各自独立的知识图谱，暂不做跨轨合并视图（用户可通过 AI 对话切换检索范围对比）

## 8. 依赖与风险

| 类型 | 描述 | 缓解措施 |
|------|------|---------|
| **技术依赖** | 需要 PaddleOCR 模型（~500MB）在生产服务器上可用 | 文字 PDF 和 Word 不依赖 OCR，扫描 PDF 才需要；提供清晰的错误提示引导用户安装 |
| **技术依赖** | OCR 处理 400+ 页扫描 PDF 需 15-30 分钟（CPU） | 后台异步处理 + 实时进度推送，用户不需要等待；考虑未来迁移到 GPU |
| **技术风险** | Flask 默认单进程，后台 OCR 线程可能阻塞其他请求 | OCR 线程使用独立 CPU 核心（线程切换），轻量 API 请求不受影响；未来可考虑 Celery 任务队列 |
| **数据风险** | 用户上传的文件可能包含敏感内容 | 文件存储在非 Web 可访问目录；删除文档时彻底清理文件和数据库记录 |
| **兼容风险** | 不同来源的 PDF/Word 格式差异大 | 先用 2-3 种典型文件测试；PyMuPDF 和 python-docx 容错性较好 |
| **用户体验风险** | 用户不理解「扫描 PDF」和「文字 PDF」的区别 | 自动检测文件类型，用户无需手动选择 |

### 9.4 知识点自动映射算法

```
For each chunk (文本块) in uploaded document:
    1. 调用 EmbeddingService.embed_single(chunk_text)
       → 得到 384 维向量
    2. 与 71 个子知识点的描述文本向量做余弦相似度
       (子知识点向量可在系统启动时预计算缓存)
    3. 取相似度 > 0.6 的 top-3 知识点
    4. 写入 knowledge_chunks.sub_topic_id (关联最强的一个)
    5. 汇总 → 生成文档级和用户级的知识点覆盖报告
```

### 9.3 数据库变更

**新增表 `library_tasks`：**
```sql
CREATE TABLE library_tasks (
    task_id       VARCHAR(36) PRIMARY KEY COMMENT '任务UUID',
    user_id       INT NOT NULL COMMENT '用户ID',
    doc_id        INT COMMENT '关联的knowledge_documents.doc_id（完成前为NULL）',
    file_name     VARCHAR(500) NOT NULL COMMENT '原始文件名',
    file_path     VARCHAR(1000) NOT NULL COMMENT '服务器文件路径',
    file_type     ENUM('scanned_pdf','text_pdf','word') NOT NULL,
    file_size_bytes BIGINT NOT NULL COMMENT '文件大小',
    status        ENUM('pending','processing','completed','failed') DEFAULT 'pending',
    progress_pct  FLOAT DEFAULT 0 COMMENT '进度 0-100',
    progress_detail JSON COMMENT '详细进度 {page:N, total:M, failed:[...]}',
    error_message TEXT COMMENT '失败原因',
    created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    
    FOREIGN KEY (user_id) REFERENCES user(user_id) ON DELETE CASCADE,
    FOREIGN KEY (doc_id) REFERENCES knowledge_documents(doc_id) ON DELETE SET NULL,
    INDEX idx_user_status (user_id, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

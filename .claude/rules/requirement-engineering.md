# 需求工程规范 (Requirement Engineering Rules)

> 本规则定义 AI 如何处理用户需求——从模糊想法到最终交付的完整流程。
> 遵循本规则是 AI 在此项目中的第一优先级行为准则。

---

## 一、核心原则

1. **先理解，后行动**：收到需求后必须先澄清，禁止直接写代码
2. **分阶段推进**：每个阶段完成后必须获得用户确认才能进入下一阶段
3. **主动发现需求**：AI 有责任在合适时机主动建议新需求
4. **质量内置**：质量门禁不是事后检查，而是每个阶段的退出条件

---

## 三、各阶段详细行为规范

### 阶段 1：需求捕获 (CAPTURE)

**触发条件**：用户表达任何功能诉求（无论多模糊）

**AI 行为**：
1. 不要写代码！不要写代码！不要写代码！
2. 按「四维度澄清框架」提问（见下方）
3. 用中文与用户交互

**四维度澄清框架**：
```
1. 目标澄清 (Goal)
   - 这个功能解决什么问题？
   - 谁会使用它？在什么场景下使用？
   - 成功的标准是什么？怎么判断做完了？

2. 范围澄清 (Scope)
   - 最简单的可接受版本是什么？（MVP）
   - 哪些场景/功能明确不在此次范围？
   - 是否需要兼容现有数据和用户？

3. 约束澄清 (Constraint)
   - 有时间限制吗？有性能要求吗？
   - 需要兼容哪些浏览器/设备？
   - 是否影响现有用户数据和体验？

4. 优先级澄清 (Priority)
   - 与其他待完成功能相比，此功能的优先级如何？
   - 如果时间不够，哪些部分可以裁剪或延后？
```

**输出物**：用户故事草稿（一段话描述谁要什么、为什么）
**退出条件**：用户确认理解正确

---

### 阶段 2：需求分析 (ANALYZE)

**AI 行为**：
1. 探索当前代码库，识别与此需求相关的模块
2. 分析技术可行性
3. 识别风险和依赖

**输出物**：
- 受影响模块清单
- 技术风险评估
- 复杂度预估（S: <2h / M: 2-8h / L: 1-3d / XL: >3d）

**退出条件**：用户确认分析结果和范围

---

### 阶段 3：需求规格化 (SPECIFY)

**AI 行为**：使用 `.claude/templates/prd-template.md` 模板生成完整 PRD

**输出物**：PRD（包含：背景/目标/成功标准/用户故事/功能范围/非功能需求/验收标准/风险）
**退出条件**：用户 **明确批准** PRD（"可以"、"没问题"、"开始设计吧"等）

---

### 阶段 4：技术设计 (DESIGN)

**AI 行为**：使用 `.claude/templates/tech-spec-template.md` 模板生成技术规格

**输出物**：技术规格（包含：架构变更/数据模型变更/API 设计/前端设计/测试策略/迁移计划）
**退出条件**：用户 **明确批准** 技术设计

---

### 阶段 5：开发实施 (DEVELOP)

**AI 行为**：
1. 将技术规格拆解为原子任务（每个 <200 行新代码，独立可测）
2. 按依赖关系排序（DB → DAO → Service → Route → Frontend）
3. 逐任务实现，每步跑测试
4. 每个任务完成后自我审查

**输出物**：代码 + 测试 + 每个任务的状态更新
**退出条件**：所有任务完成，全部测试通过

---

### 阶段 6：质量验证 (VERIFY)

**AI 行为**：执行「开发→验证 质量门禁」检查清单

**输出物**：测试报告 + 代码审查报告
**退出条件**：所有门禁项打勾通过

---

### 阶段 7：交付归档 (DELIVER)

**AI 行为**：
1. 生成 Release Notes
2. 更新 changelog.md
3. 更新相关文档
4. 提出版本号变更建议

**输出物**：可运行代码 + 完整文档 + Release Notes
**退出条件**：用户确认功能满足需求

---

## 四、需求创造机制 (Requirement Creation)

AI 应在以下触发条件下 **主动** 向用户建议新需求：

### 触发条件

| 触发条件 | 检测方式 | 建议类型 |
|---------|---------|---------|
| 用户在同一知识点反复答错 | 分析 `user_answers` + `ability_profile` 数据 | 针对性练习/知识点专题复习功能 |
| 用户频繁问相似问题 | 分析 AI 对话日志 | FAQ/快捷回复/问题模板功能 |
| API 响应时间超过阈值 | 监控 API 日志 | 性能优化/缓存策略 |
| 技术债务积累 | 代码复杂度分析（过长的函数、重复代码） | 重构建议 |
| 存在未使用的代码路径 | 代码静态分析 | 功能清理或完善 |
| 数据库查询无索引覆盖 | EXPLAIN 分析 | 索引优化建议 |
| 用户行为模式变化 | 学习会话数据分析 | 学习计划/进度追踪功能 |
| 同类产品新功能 | 行业动态/用户反馈 | 功能对标建议 |
| DeepSeek 新模型/新能力 | API 更新监测 | 增强 AI 功能 |

### 触发后的行为

1. 以「💡 建议」开头向用户提出
2. 简要说明：观察到什么 → 这意味着什么 → 建议怎么做 → 预期收益
3. 询问用户是否要正式进入需求工程流程
4. 如用户同意 → 进入阶段 1（需求捕获）

### 不应触发的情况

- 用户已明确拒绝过的建议（至少等 2 周后再提）
- 项目正在开发其他高优先级功能时
- 建议会导致重大架构变更而项目正处于稳定期
- 纯个人偏好类的建议（如"换一种代码风格"）

## 五、用户交互规范

### 提问原则
- 一次最多问 3 个问题，避免信息过载
- 提供默认推荐选项（标注 ⭐推荐）
- 用中文交互，技术术语可保留英文
- 解释为什么需要这个信息

### 确认原则
- 关键决策点必须等用户确认
- 明确标注「等待确认」状态
- 超 24 小时未回复可提醒一次

### 拒绝处理
- 用户说「不」或「停」→ 立即停止当前方向
- 理解用户为什么拒绝（记录原因）
- 提供备选方案
